NESSO Safety Monitoring System

IoT-based worker safety monitoring using wearable NESSO sensors, BLE, Python and an interactive Flask dashboard.

Project overview

The NESSO Safety Monitoring System is an IoT-based project developed to monitor worker movements and identify potential workplace safety incidents using wearable NESSO sensors. Four NESSO devices, worn on the workers' hips, read accelerometer and gyroscope data from a BMI270 motion sensor at 2 Hz and transmit the readings to a laptop through Bluetooth Low Energy (BLE). A Python application validates and cleans the incoming data, calculates movement features, and uses threshold-based logic to classify worker activities (Standing, Walking, Running) and safety events such as Near Miss, Slip/Trip/Fall (STF), and Fall From Height (FFH). Processed readings and detected events are stored in an SQLite database and displayed through an interactive Flask web dashboard. A separate version of the dashboard was deployed using Render for browser-based access to the stored dataset, while live BLE sensor collection continues to run locally.

01

The problem

Raw sensor readings are difficult to interpret directly, especially when multiple workers and large amounts of historical data are involved. The project needed a way to collect motion data, detect possible safety incidents, store the results and make them easy to inspect.

02

The solution

Four NESSO devices collect accelerometer and gyroscope readings at 2 Hz and send them to a laptop using BLE. Python first cleans the data, rejecting incomplete, non-numeric, out-of-range and duplicate packets, then calculates acceleration magnitude √(ax²+ay²+az²) and gyroscope magnitude √(gx²+gy²+gz²). Threshold-based rules label each reading as Standing, Walking, Running, Near Miss, STF or FFH. The processed records are stored in SQLite and presented through a Flask dashboard for searching, filtering, monitoring and analysis.

03

Safety event analysis

Across the four monitored workers, the dashboard surfaced clear patterns in event frequency and severity.

  • 1,135 Near Miss events: the most frequent category, where a worker almost slipped or tripped but recovered.
  • 700 STF events: slips, trips and falls remain a significant concern.
  • 190 FFH events: the least frequent but highest-severity category, needing immediate attention.
  • All four workers were mostly classified as Standing, with acceleration close to 1.0 g; gyroscope readings captured subtle orientation changes.
04

Design decisions

  • SQLite over PostgreSQL: lightweight and simple to deploy for a four-worker prototype. PostgreSQL would suit larger deployments with more concurrent users and higher data volumes.
  • BLE over Wi-Fi with MQTT: easy to configure for a small local setup. MQTT would let sensors send data straight to a central server, removing the dependency on one laptop.
05

Challenges and fixes

  • Connecting four devices at once: gave each NESSO a unique BLE identity and managed all four streams centrally in Python on one laptop.
  • Too many Near Miss detections: tested real readings and tuned the acceleration and gyroscope thresholds so normal movement was separated from genuine events.
  • Combining old and live data: imported the historical dataset into SQLite so new live BLE readings are stored alongside it and analysed together.
  • Finding records quickly: used SQL queries behind worker search, date/time filters and per-event filters.
  • Remote access: deployed the Flask dashboard on Render with a public link, while live collection stays on the laptop the sensors connect to.
